# Encrypted database and Storage recovery tooling

This offline operator tool packages an existing PostgreSQL custom-format dump **and actual bytes for every object across every Storage bucket**, including non-CMS data. A database dump alone does not contain Storage object bytes: https://supabase.com/docs/guides/platform/backups. It does not export live Production, restore a project, reconcile security or authorize a release. No web route can invoke it.

## Secure operator procedure

1. Select an owner-approved restricted backup location outside every Git checkout. Use the established full-project database export procedure with credentials provided through a secure operator session, never command arguments, files, chat or logs. Verify pg_restore can enumerate and restore the dump. `PGDMP` magic checked by this packager establishes format only, not a complete/restorable backup. Existing `backup-production-free-plan.ps1` exports only the database; do not mistake it for this combined recovery package.
2. Export an independent inventory of **all** Storage buckets and objects from the same project, including bucket configuration/policies in the database/security export. Download every object's bytes into that restricted folder. Quiesce writes or independently compare before/after source inventories, object versions and the database snapshot; abort on drift. The tool checks the supplied inventory against packaged object names and sizes; it cannot prove that a caller-supplied inventory includes the entire live service.
3. Keep the source inventory and operator configuration outside Git. Inventory JSON shape: `{ "capturedAt": "ISO timestamp", "buckets": ["bucket-id"], "objects": [{"bucket":"bucket-id","key":"folder/object","bytes":123}] }`. Empty buckets belong in the bucket list; zero-byte objects are supported. Config shape: `{ "projectRef":"20-letter-ref", "databaseDumpPath":"absolute restricted dump path", "storageInventoryPath":"absolute restricted inventory path", "storageObjects":[{"bucket":"bucket-id","key":"folder/object","path":"absolute restricted byte file"}], "encryptedBundlePath":"absolute encrypted output path" }`. No passwords, tokens or keys in this configuration. Raw combined database/object size limit is 128 MB; larger backups require a separately reviewed streaming tool, not omission of data.
4. Have the operator's secret store inject a randomly generated 32-byte key as `CMS_RECOVERY_KEY_BASE64` into this process only. Escrow the key independently from the backup using the owner's approved recovery key custody. Never print the key or put it in shell history. Run `node scripts/seal-recovery-bundle.mjs seal <restricted-config> <new-encrypted-output>`. It uses AES-256-GCM with a fresh nonce and authenticates the encrypted manifest, database and Storage hashes. It refuses Git paths, overwrites and incomplete/mismatched inventories. Plaintext is never written by this tool. Existing export files remain sensitive and must stay under restricted OS access controls; mode 0600 alone does not establish Windows ACLs.
5. Copy the encrypted artifact to an independently recoverable owner-approved **offsite** repository. From a separate operator session/device, retrieve a fresh copy and securely obtain the escrowed key. Run `node scripts/seal-recovery-bundle.mjs verify-offsite <restricted-config> <retrieved-copy>`. It compares encrypted SHA-256, authenticates/decrypts the retrieved bytes and checks database/object checksums and project identity. The printed result contains no content or credentials. Same-file verification is refused. Storage-provider identity, durability, access and genuine offsite location require independent operator evidence; the program cannot infer physical custody from a local path.
6. In a new, empty, owner-approved project, independently restore that retrieved package's database and **all** object bytes, with publication, schedules, diagnostic grants and external integrations disabled. Use a restricted operator process with `openRecoveryBundle`; it returns decrypted bytes in memory and is not a web endpoint. Do not execute SQL from a recovery package automatically. Test representative rows/Auth behavior, every Storage checksum and object count, private/public access, schema/constraints/triggers/functions/RLS/effective ACLs, revoked roles, app tenant isolation and rollback. Record source and target project identities, encrypted artifact hash, time, exact source inventory and the independent operator's signed evidence. Do not restore into existing Staging or Production. The packager's tests and readback output are **not** this rehearsal.
7. Only after verified offsite custody, successful independent restore and schema/security reconciliation should the owner approve a separate exact Production migration/build/adapter release. Neither a package nor a successful readback unlocks production: both `independentRestoreRehearsal` and `productionReleaseAuthorized` remain `false` in tool output. Held manuscripts still require separate per-article revision authorization after release.

## Owner authorization wording when the operator and destination are identified

“I authorize a read-only Production database and all-Storage backup to [approved offsite repository], with recovery key held separately in [approved secret store], and an independent restore into [approved empty project]. Do not migrate Production, switch the public site or publish articles.”

That authorizes only the backup/rehearsal scope and any separately specified cost. Production release approval follows successful evidence review and must identify exact migrations, build and public delivery target. This tool was tested only with synthetic bytes, including tamper/wrong-key/missing-object/empty-bucket/zero-byte checks and an isolated command-line round trip. No Production backup or independent hosted restore has been verified.
