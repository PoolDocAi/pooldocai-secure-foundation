**Decision date:** 2026-10-24. **Status:** binding product acceptance specification, NOT proof of implementation or authority to deploy.
**Permitted launch deferrals (owner amendment 2026-10-24):** (1) customer payment processing / checkout / subscription billing, including automatic paid seat and pooled-session add-on purchases; and (2) optional outbound SMS/text-message notifications and SMS delivery of customer links. All other advertised and agreed features—including reliable transactional and service-request email notifications and installed-PWA in-app/push notifications—must work before launch. Existing owner-approved prices/quotas remain commercially fixed (see `docs/approved-pricing-and-entitlements-2026-10-24.md`). A manually provisioned pilot/early-access account may work without payment; do not silently activate Stripe. ## 1. Durable owner launch rule
**When PoolDocAI launches publicly at its own `pooldocai.com` domain (or another explicitly selected owned domain), EVERY featured or advertised nonbilling user workflow must be implemented, secure, integrated and validated end to end.** A mock UI, feature chip, placeholder, untested Edge Function, READY UI-only preview, green syntax build, unchecked checkbox or database table does NOT count as a working feature. Includes **REAL EMAIL AND INSTALLED-APP NOTIFICATIONS** (in-app inbox + permission-based Web Push where supported), not merely a settings toggle, row in a database or a device-local reminder. **SMS transport, Twilio signup, carrier registration and SMS-sent links may remain clearly labeled pending**. Includes working tech + homeowner troubleshooting and complete document ingestion/retrieval. The owner has NOT authorized launch now, production code merge, production DB writes, commercial SMS spend or enabling payments. Keep launch as a gated event needing separate explicit owner approval after passing documented tests.

Only billable financial transactions and optional SMS delivery are exempt; **seat permissions, access controls, monthly pooled case metering, plan behavior for manually provisioned pilot accounts, trial expiry and usage dashboards are NOT exempt** merely because paid billing is disabled.

### Minimum installed-app notification architecture (launch-critical; not existing code)
1. Backend: durable `app_notifications` inbox and `push_subscriptions` (or equivalent), each scoped to the authenticated company and user; restricted RLS and explicit member role checks; no client-side direct cross-tenant dispatch.
2. Delivery: server-generated notification events for new homeowner service requests, company-assigned work, user-invite/account changes, and relevant document processing status/failure and operational alerts. Define source event IDs with unique-per-recipient idempotency, queue/retry/outage tracking, preference rules and minimal private content.
3. Web/PWA: a visible notifications badge/inbox with read/unread, dismiss and deep-link navigation; user-triggered Push permission request; service worker `push`, `notificationclick` and `showNotification`; VAPID or equivalent standard encrypted Web Push credentials held server-side. Subscription must be authorized, device/user/tenant-scoped, revocable on logout/member suspension and expire or purge stale endpoints. No popup before meaningful user action.
4. Supported platforms: verify installed Android/desktop PWA Web Push; on iPhone/iPad test Add-to-Home-Screen PWA on iOS/iPadOS 16.4+ with user permission. Honor unsupported/denied permissions without blocking the app: email AND in-app inbox continue working. Do not promise push alerts where OS/browser settings prohibit them.
5. Reliability/security: when app is closed, push shows as native-style OS alert on supported subscribed device; when opened, inbox lists same authorized event without duplicate unread entries. Clicking navigates to authenticated correct-company service request/job, never places customer's private data in notification bodies, URLs or logs. Denied/revoked/failed delivery is visible in an owner/company monitoring log; email stays available.
6. Email: use verified `pooldocai.com` sender + Resend or production SMTP. Deliver invite/reset emails and opted-in service-request/work alerts to external domains. Store recipient/tenant delivery outcome with minimal PII; no invented sent/delivered status. Email must work if Web Push denied.

Browser/CI unit tests alone DO NOT establish actual delivery.
8. **SMS deferred:** Any existing `sms_notifications_enabled` options must be disabled/hidden or marked "Coming later"; they must not become an apparent available alert route.
